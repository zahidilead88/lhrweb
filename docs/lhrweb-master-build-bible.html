Part 0
The Product
What we are building and why, in enough detail that the code decisions later make sense.

What LHRWEB Is

0.1

LHRWEB is a Website Operating System: one visual workspace where anyone can design, build, manage, and publish a professional website without writing code. It occupies the space around Webflow, Framer, and Figma-Sites, but the scope is wider than "a site builder" — the intent is that a business goes from idea → live website → running online store without leaving the tool or hiring a developer.

The product is built out of Lahore and connects to your other properties (Websouls, Futuresouls). It is a real full-stack platform: a public marketing site, an admin panel, a customer dashboard, and the AI-powered builder — backed by Next.js 15, Express.js, MongoDB, Gemini 2.5 Flash, and Stripe.

◆
The single most important architectural idea: one builder, one engine, two doors. Everything else follows from that.

The Four Layers

0.2
1 · Public marketing site
app/(frontend)/ — LHRWEB's own front door: landing, pricing, features, lead capture.
2 · Customer dashboard
app/(dashboard)/ — each user manages their sites, Stripe billing (starter/pro), profile, support.
3 · Admin panel
app/admin/ — you manage all customer sites (owner, slug, plan, status, preview), leads, and content.
4 · The Builder
app/builder/ — the AI + visual editor where sites are actually made. This document is mostly about this layer.

Published customer sites are served at slug.lhrweb.app via subdomain routing (Next.js middleware.ts), or on a connected custom domain with DNS verification. Users can also export clean HTML/CSS as a ZIP.

Two Modes, One Engine

0.3

There is one builder with two entry experiences — not two products. Internally they're a single flag, canvasMode: 'flow' | 'free'.

Guided Builder  canvasMode:'flow'
The fast path. Start from AI, a template, or prebuilt sections. AI writes a complete first-draft site from a prompt in ~1 minute; the user refines section by section. For people who want a finished site quickly.
Visual Design Studio  canvasMode:'free'
The Figma-style infinite canvas. Draw anything on artboards (frames) with real tools: pan/zoom 5–800%, rulers, snap guides, alignment, layers. For people who want pixel control from scratch.

Both run on one shared engine: one data model (ElementNode tree), one renderer (generateHTML + generateCSS), one history/undo, one publish path. The "modes" are two doors into the same room — the user should never feel they switched apps. In UI/marketing they're called Guided Builder and Visual Design Studio; in code the enum stays 'flow'/'free' (do not rename it).

The AI Layer

0.4

The AI is a serious subsystem, not a bolt-on — and per your AI-ENGINE-GUIDE it is largely built. It generates whole sites, generates individual sections, rewrites copy, regenerates layouts, produces SEO metadata, and applies themes.

Under the hood it has a real spine: a structured 5-block prompt system, JSON output validation, a 3-stage repair loop (local jsonrepair → low-temp model repair → regenerate) that fixes malformed responses before they touch a site, an AI memory that stores distilled facts rather than transcripts, and a fallback ladder so a failed generation never destroys existing content.

✓
Governing principle: "AI is an intern." It drafts; it never silently deletes pages, saves, or publishes. Generate → validate → apply is always atomic.

Canvas → Website Intelligence (the differentiator)

0.5

The thing that separates LHRWEB from "Figma that exports HTML": because every canvas object carries website semantics, you can right-click a plain rectangle and promote it up a ladder.

Rectangle → Section → Hero → Navbar → Product Card → CMS List → Component

A drawing becomes real website structure. Figma can't do this — its objects are just shapes; yours know what a "Product Card" or "CMS List" is. This is the payoff for building everything on one semantic data model, and it's cheap to add precisely because every rung already exists as something the builder can render (Part 5, Phase 5).

The End-to-End User Journey

0.6
New Website   → choose ○ AI   ○ Template   ○ Blank Canvas   → land in the Visual Workspace (draw · style · arrange · add sections · bind CMS · add products)   → Publish → live at slug.lhrweb.app, pixel-accurate to the design   → optionally Export code · connect a custom domain · sell products

Today this journey breaks at "Publish" for anyone who used the Visual Design Studio — that's the blocker in Part 2. Everything from Part 1 onward is about making this journey real end to end.

Part 1
Architecture & Data Model
The shapes and pipelines the whole build rests on. Understand these and every later code change is obvious.

The Data Model

1.1

One tree of nodes describes every page. The same shape is produced by AI, by the flow builder, and by the free canvas — which is what lets one renderer serve all of them.

types/builder.ts — the core shapes interface ElementNode { id: string; // el-XXXXXXXX tag: HTMLTag; // section | div | h1..h6 | p | img | button | a | ... label?: string; // semantic name shown as a badge (Hero, Navbar) content?: string; // text for leaf nodes styles: Styles; // { desktop, tablet?, mobile? } responsive style sets attrs?: Record<string,string>; // href, src, alt, ... layout?: FreeLayout; // ONLY on free-canvas nodes (absolute x/y/w/h) children: ElementNode[]; // always present (empty [] for leaves) componentId?: string; // set on instances (Phase 4) cmsField?: string; // binds content to a CMS field (Part 6) } interface FreeLayout { // the free-canvas positioning envelope x: number; y: number; width: number; height?: number; rotation?: number; zIndex?: number; aspectLocked?: boolean; // last two added in Phase 1 } interface Frame { // a Figma-style artboard id: string; // frame-XXXXXXXX name: string; canvasX: number; canvasY: number; width: number; height: number; background?: string; children: ElementNode[]; // the elements drawn inside this artboard autoLayout?: AutoLayout; // added in Phase 3 } interface BuilderProject { // the persisted document (Mongo) _id: string; userId: string; status: 'empty'|'generating'|'ready'; slug: string; canvasMode: 'flow'|'free'; pages: { id; name; slug; blocks: Block[]; elements: ElementNode[] }[]; classes: StyleClass[]; tokens: SiteTokens; savedSections: SavedSection[]; canvasState: { frames: Frame[]; zoom; panX; panY }; // the free-canvas store components?: Component[]; // Phase 4 }
⚠
The one field that matters most for the blocker: layout lives on free-canvas nodes and holds absolute coordinates. The published renderer is flow-based and must never receive a raw layout — it gets converted to CSS. That conversion is the fix in Part 2.

The Two-Store Model (read this twice)

1.2

There are two places element data can live, and understanding the split explains the entire blocker.

StoreHoldsRead by
page.elements[]The publishable page tree (flow-positioned)The live site — by-slug → generateHTML
canvasState.frames[]The editable free-canvas (artboards + absolute children)The builder canvas only — re-open to keep designing

Flow mode writes page.elements directly, so it publishes fine. Free mode writes only canvasState.frames. Nothing converts frames → page.elements, so free-mode designs never reach the renderer. The fix is not to change the renderer — it's to write page.elements on save from the active frame, so both stores stay populated.

The Render Pipeline

1.3
page.elements[]   → generateHTML(elements) // recursive: each node → tag with data-id, class, data-animate   → generateCSS(elements, classes, tokens) // 3-layer cascade: :root tokens → .class → [data-id]   → inline <style> + HTML string // stored/served by by-slug (status=ready)

Styles cascade in specificity order — token vars at :root, then named classes, then per-element overrides, then breakpoints (tablet max-width:991px, mobile 479px). This is already built and working for flow pages; the blocker fix simply feeds it the free-mode content it's currently starved of.

Part 2
The One Blocker — Free Mode Publishes Blank
The single highest-value fix. Do this first; nothing else reaches users until it's done.

Why It Happens

2.1
User draws in Free Mode   → elements live in frames[].children // page.tsx `frames` state   → handleSave() serializes frames → canvasState   → PUT /project/settings stores canvasState MEANWHILE the published site:   GET /by-slug/:slug → generateHTML(page.elements) // never reads canvasState   → free-only design ⇒ page.elements empty ⇒ BLANK SITE

STRUCTURE.md line 288 states canvasState.frames is "authoritative" — but only for the canvas. The renderer reads page.elements. No function bridges them. ConvertModal targets savedSections (wrong target); blockToElements goes Flow→Free (wrong direction).

Fix Step 1 — New File

2.2

CREATE  lib/frameToElements.ts

A pure function that flattens one frame into a publishable ElementNode[]: the frame becomes a <section>, and every child's absolute layout is converted into CSS positioning and then stripped, because the renderer is flow-based.

lib/frameToElements.ts — complete import { ElementNode, Frame } from '@/types/builder'; /** * Convert one free-canvas Frame into a page-ready ElementNode[]. * Frame → <section>; children keep their visual position via absolute CSS. * `layout` is removed from every node so the flow renderer never sees it. */ export function frameToElements(frame: Frame): ElementNode[] { const section: ElementNode = { id: `el-sec-${frame.id.slice(-8)}`, tag: 'section', label: frame.name, styles: { desktop: { position: 'relative', width: '100%', minHeight: `${frame.height}px`, background: frame.background ?? '#ffffff', overflow: 'hidden', }, }, children: frame.children.map(mapNode), }; return [section]; } function mapNode(node: ElementNode): ElementNode { const { layout, ...rest } = node; return { ...rest, styles: { ...node.styles, desktop: { ...node.styles.desktop, ...(layout ? { position: 'absolute', left: `${layout.x}px`, top: `${layout.y}px`, width: `${layout.width}px`, ...(layout.height ? { height: `${layout.height}px` } : {}), ...(layout.rotation ? { transform: `rotate(${layout.rotation}deg)` } : {}), ...(layout.zIndex != null ? { zIndex: String(layout.zIndex) } : {}), } : {}), }, }, children: node.children.map(mapNode), }; }
⚠
v1 uses absolute positioning so publish is pixel-accurate immediately. Phase 3 upgrades this: frames with autoLayout emit flex flow instead, for better responsive output. Ship absolute first — it's correct and it unblocks everything.

Fix Step 2 — handleSave

2.3

EDIT  app/builder/page.tsx → handleSave()

Before the pages PUT, if in free mode, sync the frame that maps to the current page into page.elements. Match frame→page by name; fall back to the first frame.

app/builder/page.tsx — inside handleSave(), before the pages PUT import { frameToElements } from '@/lib/frameToElements'; let elementsToSave = elements; // existing V2 elements (flow) if (canvasMode === 'free' && frames.length > 0) { const page = project.pages.find(p => p.id === selectedId); const frame = frames.find( f => f.name.toLowerCase() === page?.name.toLowerCase() ) ?? frames[0]; if (frame) elementsToSave = frameToElements(frame); } // existing PUT — now carries the synced, publishable elements await apiFetch(`/api/builder/project/pages/${selectedId}?projectId=${project._id}`, { method: 'PUT', body: JSON.stringify({ blocks, elements: elementsToSave }), }); // canvasState (raw frames) still saved via /settings as before, // so the CANVAS stays fully editable next session.
✓
The whole insight in one line: save must write both stores. canvasState.frames keeps the canvas editable; page.elements makes it publishable. They are not redundant — they serve different readers.
Optional — explicit "Use frame on page" button

Add a button in CanvasToolbar.tsx that runs the same frameToElements sync on demand + toasts "Home page updated." Gives users an explicit frame → page mental model instead of it happening silently. Wire it to the same helper.

Part 3
Six Launch-Blocking Bugs
Each can corrupt data, leak data, or silently lose a user's work. All must land before real users touch the product.

The Six Fixes (with code)

3.1
Bug 1 — Silent save failure  page.tsx

A failed save can still flip saved=true, so the user believes work is safe, then closes the tab. Only claim success on full success; snapshot to localStorage on failure.

try { setSaving(true); await Promise.all([/* page PUT, classes, tokens, settings */]); setSaved(true); // ONLY on full success setTimeout(() => setSaved(false), 2500); } catch (e) { setSaved(false); // never claim success on error localStorage.setItem( `lhrweb_recovery_${project._id}`, JSON.stringify({ elements, frames, at: Date.now() }) ); toast.error('Save failed — your work is safe here. Retrying…'); // schedule 3 auto-retries at 2s / 5s / 15s } finally { setSaving(false); saveInFlight.current = false; // release the lock }
Bug 2 — API URL localhost fallback  lib/api.ts + app.js

An unset NEXT_PUBLIC_API_URL silently falls back to localhost — a misconfigured prod deploy then talks to nothing. Fail loud instead.

// lib/api.ts const API = process.env.NEXT_PUBLIC_API_URL; if (!API && process.env.NODE_ENV === 'production') { throw new Error('NEXT_PUBLIC_API_URL not set — refusing to run.'); } export const apiUrl = (p) => `${API ?? 'http://localhost:8000'}${p}`; // backend app.js mirrors this: refuse to boot if MONGODB_URI / JWT / STRIPE keys missing. // Also: make page.tsx use apiFetch/apiUrl everywhere (STRUCTURE notes it doesn't yet).
Bug 3 — V1 export crash  routes/export.js
// const { archiver } = require('archiver'); // wrong — not a named export const archiver = require('archiver'); // correct // build the ZIP to a buffer, THEN stream it — never pipe archiver straight to // the response, or a mid-stream throw ships a corrupt partial file.
Bug 4 — Admin password re-upsert on boot  app.js
const existing = await AdminUser.findOne({ email: ADMIN_EMAIL }); if (!existing) { await AdminUser.create({ email: ADMIN_EMAIL, password: await hash(seedPw) }); } // create-only. Never upsert WITH password on boot, or a rotated password reverts.
Bug 5 — Wide-open CORS  app.js
app.use(cors({ origin: [process.env.APP_URL, /\.lhrweb\.app$/], // app + published subdomains credentials: true, })); app.use(helmet()); // + CSP. Published sites are same-origin renders — no wildcard needed.
Bug 6 — No AbortController on builder fetches  page.tsx

Rapid page switches leave in-flight requests that resolve into stale state (a slow load overwrites a newer selection). Thread a signal; abort on cleanup.

const ac = new AbortController(); apiFetch(url, { signal: ac.signal }); // cleanup (unmount / before next load): ac.abort();
✓
Part 2 + these six = the ship gate. They map to the Round 4 launch checklist. When all seven are green, LHRWEB is safe for real users even before Phase 1–5 depth lands.

Ecommerce Models & Rules

6.1

Server-authoritative commerce. The client never sets prices or creates orders; the server and Stripe webhook are the source of truth.

core commerce shapes (Mongo) Product { projectId, title, price:Float, images[], variants[], inventory, policy:'deny'|'continue'|'hide' } Variant = Cartesian product of options (Size × Color → SKUs) Cart { cartToken:UUID, projectId, items[{productId, variantId, qty, priceSnapshot}], ttl:30d } Order { projectId, items[], total, status, timeline[] } // created ONLY by webhook
RuleWhy
Cart lives server-sideClient holds only cartToken in localStorage lhrweb_cart_token_{projectId}; prices are snapshotted server-side
Order created by webhook onlyNever trust the browser; the Stripe payment_succeeded webhook creates the order
Inventory decrements at payment successAtomic $inc; oversell flagged hasOversell, never silently allowed
Status machine is forward-onlypending→processing→shipped→delivered / cancelled→refunded; no backward transitions

Routes live in routes/builder.js (or a new routes/commerce.js): product CRUD, cart add/update, checkout PaymentIntent (server-calculated), plus the webhook handler. Customer accounts are separate from platform Users, per-project scoped, with their own JWT secret.

CMS Binding

6.2

Dynamic content: collections of entries, bound to elements, resolved into real HTML at publish.

CMS shapes + resolution CmsCollection { projectId, name, fields[{key, type}] } CmsEntry { collectionId, values:{ [key]: any }, slug } // binding: an ElementNode gets cmsField:'title' → its content comes from the entry. // repeater: a node with attrs.__repeat = collectionId renders once per entry. function resolveCmsBindings(el: ElementNode, entry: CmsEntry): ElementNode { const content = el.cmsField ? entry.values[el.cmsField] ?? el.content : el.content; return { ...el, content, children: el.children.map(c => resolveCmsBindings(c, entry)) }; } // pipeline: resolveCmsBindings runs BEFORE generateHTML, so the renderer stays // dumb — it only ever sees fully-resolved ElementNodes. Blog is a built-in collection.

This is where Product Card and CMS List promotions (Phase 5) pay off: a promoted card becomes a repeater over a collection, so one design renders an entire catalog or blog index.
